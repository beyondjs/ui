# Beyond UI agent instructions

This is the canonical instruction source for this independent repository. Read [README.md](README.md), [architecture](docs/architecture.md) and [validation](docs/validation.md) before making changes. Tool bridges must remain thin pointers here.

- UI owns reusable components and foundations across products. Support the intended React and plain JavaScript DOM consumers without selecting an exclusive framework or Web Components by assumption. The September 23 scope in [architecture](docs/architecture.md#september-23-shared-experience-scope) defines the next implementation assignment, including actual cross-suite adoption; the present baseline remains documentation-only.
- Branding owns the family model, journeys, experience proposals and implementation evidence. Its `src/foundations/` is the canonical token source until an explicit extraction is implemented. Do not duplicate tokens, merge or rename Branding, change product flows or claim integration during onboarding.
- Preserve the selected branch, refs, history, remotes and uncommitted work. The initially unborn `main` is an explicit exception to Beyond Suite's coordinated `feature/next` convention. Do not create a first commit, switch branches, commit, push, deploy or publish without explicit authorization.
- Follow [coding standards](docs/coding-standards.md): source files target at most 300 lines and must not exceed 400; model responsibilities as classes with `#private` state, composed collaborators and simply named members. Avoid compound method, property, variable and parameter names; class names may be compound. Preserve public contracts. No accepted source exceptions exist yet.
- Use English and portable paths in first-party documentation and code. Keep generated/vendor material intact. Never version credentials, private machine mappings or local runtime paths.
- Follow [documentation instructions](docs/AGENTS.md); durable guides and dated evidence belong in `docs/`, temporary assignments in `docs-temp/`. Promote durable decisions before retiring temporary material.
- Follow the test organization and source-fixture rules in [validation](docs/validation.md). Distinguish source examples, harnesses and assertions; store substantive examples as physical fixtures, copy mutable fixtures into isolated temporary directories, await readiness and clean up all owned resources. Test public contracts with success, negative and recovery cases. Packages-compiled modules use `beyond test`; Engine-compiled implementation modules keep checkout-level `tests/` and use utilities validation. No compiler or runner is selected for UI yet.
- This is a library scaffold with no runnable application. Do not invent a server or a placeholder page. If an application or showcase is later commissioned, supply its root `npm run dev` and suite selector registration with the shared tooling and verify both launch paths.

## Family reference synchronization

Every assignment changing user-visible functionality, authorization/admission (including refusal meaning), navigation, visible states or recovery must assess and update the affected family representation, journeys, evidence and documentation in the same assignment. The suite's canonical policy is `docs/family-reference-synchronization.md` in the Beyond Suite repository; this is a portable locator, not a required sibling dependency. Finish with **synchronized**, **no reference impact** with a reason, or **synchronization blocked** with affected identifiers, blocker, owner/decision and remaining work. Record the evidence date/type, product revision and uncommitted state, reference/token versions and proposal approval state. If the suite is unavailable, retain the report here and return it to its owner; do not claim synchronization. Simulation does not prove product acceptance, and implementation does not approve a proposal.
